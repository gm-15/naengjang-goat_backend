# 팀원별 마무리 작업

> 이 문서는 백엔드를 먼저 전달할 때의 작업 분배 기록입니다. 이후 웹·모바일 구현을 통합했으므로 **현재 남은 확인 작업은 [최신 통합 상태](../integration/STATUS.md)**를 기준으로 확인하세요.

신규 기능 확대보다 점주 흐름 완결 우선. 취소·환불/AI/일반 알림함은 이번 작업 제외. 기준 API는 [API_CONTRACT.md](API_CONTRACT.md).

## 김건우 — 프론트·모바일

### 현재 확인한 상태

- 웹/Native의 재고·가격·발주 조회, 외부 상품 링크 이동, 구매 내용 등록 기본 화면 있음.
- 웹 `frontend/src/app/pages/LowestPriceDetailPage.tsx`, Native `mobile/src/app/(tabs)/lowest-price/[id].tsx`: 구매 기록 성공 후 `createBatchMutation`을 호출해 바로 입고 처리하는 코드 있음.
- `api/users.ts`에 FCM 토큰 등록 함수가 있지만 앱 수명주기의 실제 호출·권한·수신 연결 확인되지 않음.
- 새 POS 업로드, 배송 대기→입고 완료, 일일 운영 리포트 및 새 알림 상세 API 연결은 추가 작업 필요.
- 기존 화면 전체가 실행 시 오류라고 단정한 것이 아니라, 최신 프론트 코드와 이번 백엔드 계약의 차이를 확인한 결과임.

### 할 일 — 순서대로

1. 구매 등록 수정
   - 구매 등록 직후 `createBatchMutation` 제거. 웹·Native 모두 적용.
   - 외부 사이트 복귀 시 “주문했는지” 확인 유지. 미주문이면 아무 기록 없음.
   - 클릭 상품명 기본 입력, 연결 재료 선택, 구매 수량·단위·해당 단위당 가격 입력.
   - 포장 상품이면 포장당 크기/단위 입력. 상품 가격을 g/ml/개 단가라고 임의로 보내지 않음.
   - 성공 후 `WAITING` 표시. 재고가 그대로인 것을 화면/문구에 반영.

2. 배송 대기 및 입고 연결
   - 기존 발주 내역에 배송 대기/입고 완료 구분 또는 배송 영역 추가.
   - `deliveryStatus` 필터·추가 응답 필드 타입 반영.
   - 수령 후 입고 버튼. `expectedQuantityBase`/`inventoryUnit` 표시, 유통기한 입력.
   - `/purchase-orders/{id}/receive` 성공 후 완료 표시 및 목록·재고 갱신.
   - 실패/중복 409 안내, 버튼 중복 누름 방지. 부분 수령은 이번 버전 미지원 안내.
   - 과거 `LEGACY` 기록은 입고 완료로 추측하거나 새 입고 버튼을 노출하지 않음.

3. POS 엑셀 업로드
   - 점주가 실제 기기에서 xlsx 선택하고 multipart `file`로 업로드.
   - 영업일/양식 안내, 처리 중 상태, 서버 오류 메시지 및 이미 반영된 파일 안내.
   - 성공 후 소비량/판매 수량/판매금액 표시, 재고·판단·리포트 조회 갱신.
   - 웹과 Native 모두 지원. `Content-Type`에 boundary를 수동으로 잘못 지정하지 않음.
   - 앱 내 수동 판매등록 화면은 추가하지 않음.

4. 운영 리포트 및 발주 판단
   - 영업일별 업로드 여부·메뉴 판매 수량/금액·재료 소비량·현재 재고 표시.
   - 미업로드를 0매출 확정으로 표시하지 않음. 현재 재고는 조회 시각 표시.
   - 판매 수량을 거래 건수라고, 매출을 순이익이라고 쓰지 않음.
   - 발주 판단은 `/closing/recommendations` 연결. 단위·추천량·재고 부족 근거·가격 근거·마지막 판매 반영일 표시.
   - 판단 수량 null/판매 미반영/설정 없음/가격 없음 상태 표시. 물리적 재고와 사용 가능한 재고가 다를 수 있음을 맞춤.

5. 모바일 푸시 연결
   - Firebase native 설정 및 실제 기기 알림 권한 요청.
   - FCM native 기기 토큰 취득 → 기존 PATCH 등록 API 호출, 토큰 변경 시 갱신.
   - foreground/background/앱 종료 상태 수신 확인. Expo Push Token과 혼용 금지.
   - data의 `notificationId`로 중복 수신 방어 및 누른 뒤 알림 상세 조회→판단 화면 이동.
   - 일반 알림함/읽음 처리 화면은 이번 필수 작업으로 추가하지 않음.

### 완료 기준

- 발주 기록만으로 재고 증가 없음. 수령 후 입고 성공 시 한 번 증가.
- Native 파일 선택→POS 반영→리포트/재고 갱신 확인.
- 업로드 후와 영업 전 두 알림 실기기 수신, 알림을 눌러 해당 판단 확인.
- 웹/Native의 API 주소·JWT·오류 표시 확인. 서버 계약 보완 패치는 이미 이번 백엔드에 포함됐으므로 같은 패치를 중복 적용하지 않음.

## 심상묵 — 데이터·백엔드 보조

### 현재 제공된 자료

- 서버 demo 프로필에 합성 메뉴/BOM·초기 재고·과거 29일 판매·30일 가격 fixture 있음.
- 오늘 날짜 POS 샘플 다운로드와 HTTP 기대 숫자 검증 스크립트 있음.
- 이 자료는 시연 준비 기준이며 실제 매장/공공 시세 원본으로 표현하지 않음.

### 할 일

- 사용할 POS 양식 확정 자료 준비. 실제 양식 확보 시 프로젝트 양식으로 변환하고 메뉴코드/메뉴명 연결표 작성.
- 실제 시연 메뉴별 레시피 소모량 검증. 자동 생성된 `requiredQuantity=1` placeholder를 실제 조리량으로 확정.
- 초기 재고/유통기한/입고일, 클릭 상품의 포장 크기·가격 기준 및 재료 관리 단위(g/ml/개) 검증.
- KAMIS의 도매/소매 필드 의미, EKAPE의 가격·날짜·단위, 데이터 출처, 중복/결측·최신성 검증.
- 동일 재료라도 단위·등급·출처가 달라진 자료를 하나의 30일 평균으로 섞지 않도록 기준 확정 후 수집/정제 코드 보완.
- 온라인 최저가의 실제 상품 링크·포장 가격·환산 근거 검증. 시장 평균가를 실제 구매 가능한 상품 가격이라고 표현하지 않음.
- 시연 기대표 작성: 메뉴 판매량×레시피 소비, 재고 전후, 30일 평균, 발주량, 가격 신호. 합성 데이터 교체 시 총괄에게 새 기대 숫자 제공.
- 확정 데이터를 동일한 새 시연 DB에서 재현하는 방법 제공. 공유 DB 전체 초기화 금지.

### 완료 기준

- 데이터 출처·관측일·가격 단위와 메뉴/재료 연결표 제출.
- 기대표와 API 실제 값 일치. 실자료 부족 시 발표에 합성/미검증 범위 명시.

## 박건우 — 백엔드 총괄

### 팀원에게 넘기기 전 완료

- POS 반영·배송/입고·리포트·두 알림 서버 구현.
- 인증/가격 JSON/단위 계약 수정.
- 원자성·동시성·중복 방지·오류/소유권·알림 스케줄 검증.
- API 문서·시연 fixture·HTTP 실행 자료 전달.
- 기존 DB 업그레이드 시 bootstrap migration 적용 기준 확인.

### 팀원 작업 이후 수행

- 프론트·모바일 결과와 실제 데이터 수령 후 API 연결 E2E 검증.
- 실제 Firebase 설정/기기 토큰을 받으면 실발송 상태 및 앱 수신·화면 이동 검증.
- 연동 중 발견된 요청/단위/오류 표시 차이 수정.
- 최종 시연 DB·APK/웹·서버 실행 환경 고정, 4분 리허설 및 예비 영상 준비.

팀원이 구현하기 전에 총괄 서버 작업은 독립적으로 완료 가능. 실기기 푸시·앱 화면 E2E·실자료 결과 확인은 팀원 작업 이후 완료 가능. 팀원에게 지금 이 API와 문서를 넘겨도 되며, 그 이후 서버를 완전히 끝냈다고 방치하지 않고 통합 검증을 이어간다.
