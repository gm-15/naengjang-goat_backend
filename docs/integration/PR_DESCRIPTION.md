## 작업 목적

기존 웹·모바일은 구매 기록을 저장하자마자 재고를 늘렸고, 새 백엔드의 POS 판매 마감·일일 리포트·배송 입고 API와 연결되지 않았습니다. 최신 백엔드를 기준으로 팀원의 웹·Android 코드를 통합하고 **POS 판매 반영 → 발주 판단 → 외부 구매 기록 → 배송 대기 → 수령 입고** 흐름을 연결했습니다.

## 변경 사항

- 팀원 `feat/fcm-push-mobile`의 프론트만 `frontend/`, `mobile/`로 통합. 서버는 이 저장소 최신 main을 기준으로 유지.
- 웹·앱 구매 기록 직후 입고 호출 제거. 클릭 상품명·링크 기본 입력, 구매 단위·포장당 크기·단가·총액 확인, 배송 상태 필터와 수령 입고 연결.
- POS 엑셀 선택·즉시 반영·메뉴코드 연결·양식 다운로드 구현. 오류·동일 파일 재업로드·같은 영업일 다른 파일 충돌 안내와 재고/리포트/판단 갱신.
- 메뉴·레시피 등록/수정 API와 웹·앱 편집 화면 추가. 실제 1인분 소모량을 설정하고 기존 판매·소비 기록의 수치는 보존.
- 영업일별 판매금액·메뉴 판매수량·재료 소비량·현재 재고 리포트와 발주 판단 연결. 미업로드·설정/이력/가격 부족 상태를 구분.
- 모바일 FCM 등록·토큰 갱신·수신·알림 상세 이동 연결. 로그인 전 알림 탭 복귀, 계정/서버 전환, 현재 기기 토큰 조건부 해제와 등록 중 로그아웃 경합 처리.
- 서버 FCM 토큰 검증·소유권 이동·동시 등록 방어 추가. V010에서 빈 토큰과 중복 토큰 정리 후 토큰별 유일 소유권 적용.
- 온보딩 재요청 시 수정한 메뉴·레시피 보존, 타인 재고 배치 조회 차단, 웹 개발 프록시 및 클라이언트 CI 검사 추가.

## 검증

- Java 21 / MySQL 8 / Redis에서 백엔드 `clean test bootJar`: 43개 통과, 실패·오류·건너뜀 0.
- 웹 TypeScript 검사·프로덕션 빌드, 모바일 TypeScript·단위 검사·Android/Hermes 번들 내보내기 통과.
- 실제 Spring 서버·웹을 Chromium으로 검증: 판매 8개·64,000원·배추 소비 4,000g, 재고 **6,000 → 2,000 → 구매 기록 후 2,000 → 수령 입고 후 4,000g**.
- 중복 업로드/입고·동일 영업일 충돌·타인 자료 접근 차단, 신규 점주 온보딩·실제 레시피 수정·POS 양식 업로드·과거 소비량 보존 확인.
- 상세 수치·검사 범위는 [검증 기록](VALIDATION.md) 참고. 외부 상품 카드 응답은 검사 자료로 대체했으며 판매·구매 기록·입고는 실제 서버 API를 사용.

## 실행·적용 시 확인

- `expo-document-picker`가 추가되어 **기존 Android APK를 다시 빌드·설치**해야 함. JavaScript 번들 검증과 네이티브 APK/실기기 검증은 별도.
- 새 DB는 기존 레시피 자료 68개 메뉴를 처음 적재한 뒤 온보딩. 기본 자료는 상품 구성/포장 자료이므로 실제 메뉴별 1인분 소모량을 반드시 설정.
- 서버 Firebase 서비스 계정을 연결해 실제 폰에서 업로드 직후·영업 시작 3시간 전 알림 수신과 탭을 확인. 이번 클라우드에는 서비스 계정이 없어 실제 푸시 발송은 검증하지 않음.
- 실제 KAMIS/EKAPE/온라인 상품 가격과 POS·재고 자료의 단위·최신성 확인 필요.
- V010은 중복 토큰의 가장 큰 사용자 ID에 연결을 남김. 다른 사용자의 앱은 재실행해 자기 토큰을 다시 등록.
- 주문 취소·환불, 주문/결제 대행, 부분 수령, AI, 일반 알림함, POS 제품별 자동 변환은 이번 합의 범위에서 제외.

실행은 [실행 안내](RUNBOOK.md), 팀원별 남은 확인은 [통합 상태](STATUS.md)를 기준으로 진행합니다.
